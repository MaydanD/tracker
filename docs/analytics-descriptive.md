# Stage 7B — описательная аналитика и динамика

Версия ответа: `7B.1`. Источник: исключительно канонический
[набор Stage 7A](analytics-dataset.md), версия `7A.1`. Назначение — описать
наблюдения одной переменной, их количество, распределение, изменчивость и динамику.
Это не статистическая значимость, прогноз или оценка того, что человеку полезно.

## Архитектура и API

```python
from app.services.descriptive import get_descriptive

result = get_descriptive(
    session, start, end, ("state.mood", "state.alcohol", "daily.score"),
    today=clock.today(),
)
```

HTTP (параметр `variables` повторяется для каждой переменной):

```text
GET /api/analytics/descriptive?start=2026-09-01&end=2026-09-30&variables=state.mood&variables=state.alcohol
```

`start`, `end`, `variables` обязательны. Обе границы включительные, поддерживаются
произвольные диапазоны, месяцы, годы и диапазоны через Новый год. Ограничения:
1–1830 календарных дней, 1–64 уникальных ключа, длина ключа 1–160 символов.
Предыдущий равный период должен помещаться в Python `date`; запрос с началом
`0001-01-01` отклоняется. Нет преобразований календарных дат в timestamps/UTC.
Недели Пн–Вс; используется существующая календарная идентичность Stage 7A.

Ошибки HTTP 422 используют существующий envelope `error`, сообщение по-русски.
Неизвестный ключ (включая привычку вне объединённого диапазона) отклоняется, а не
молча игнорируется. Число ключей/границы/дубликаты проверяются до загрузки БД;
существование ключей — по загруженному динамическому реестру Stage 7A.
Запись через endpoint не поддерживается. Полная схема доступна в OpenAPI.

Ответ содержит:

- `contract_version`, `dataset_contract_version`, `today`;
- `current_period`, `previous_period`;
- `policy`: все числовые пороги текущего контракта;
- `variables`: результаты в лексикографическом порядке ключей.

Каждый результат: метаданные `variable` из Stage 7A, `summary`, `series`, `rolling`,
`comparison` (включает `current` и `previous` сводки), `trend`.
Статистика — типизированный вариант с полем `type`: numeric/ordinal, boolean или
categorical. ORM-объектов и свободных текстовых заметок в ответе нет.

Модули:

- `domain/analytics/descriptive_types.py`: immutable dataclasses и единый `POLICY`.
- `domain/analytics/descriptive.py`: чистые расчёты по реестру, ячейкам и контексту 7A.
- `services/descriptive.py`: один вызов `services.analytics.get_dataset` для
  объединения текущего и предыдущего периодов, затем чистая обработка.
- `schemas/descriptive.py`, `api/routes/descriptive.py`: JSON/OpenAPI и HTTP.

Добавлен чистый `Stage 7A builder.slice_dataset`: проекция загруженного набора на
поддиапазон. Она сохраняет недельный прогресс Stage 4, но пересчитывает **только
канонические State-агрегаты** и requested coverage из дневных ячеек 7A.
Переиспользуется один `state_week_values` в исходном builder и в проекции.
Это важно, когда сравниваемые диапазоны пересекают одну календарную неделю:
State каждого периода не должен захватывать даты другого. Версия и семантика 7A
не изменились; новых полей в исходный контракт не добавлено.

## Покрытие и отсутствие данных

Каждая сводка и каждое окно содержат `coverage` в единицах естественного зерна
переменной (дни либо недели):

| Поле | Определение |
| --- | --- |
| `total_count` | Все ячейки периода/доступной части окна |
| `observed_count` | Число `present` |
| `missing_count` | `source_missing + field_missing + no_observations` |
| `eligible_count` | `observed_count + missing_count` |
| `unavailable_count` | Все непредставленные значения, включая неприменимые/будущие |
| `ratio` | `observed_count / eligible_count`, либо null при нуле eligible |
| `counts_by_availability` | Все состояния 7A с отдельными счётчиками, включая нули |

`not_applicable`, `future`, `no_obligations` не входят в eligible и не считаются
неудачами. `present` имеет именно смысл 7A: это может быть наблюдение, вычисление,
известный план или календарный признак, а не обязательно запись пользователя.
Поэтому будущий известный план может быть `present`; его происхождение остаётся в
`variable.source`, а временная незавершённость отдельно обозначена `incomplete`.

Недельные State-точки дополнительно содержат `source_coverage` по **дневным исходным
ячейкам** запрошенного среза. В сводке эти непересекающиеся покрытия объединяются.
Например, четыре недельных средних, каждое по одному дню, дают coverage=4/4 по
неделям, но source_coverage=4/28 по дням. Для сравнения/тренда/rolling недельных
средних проверяется также минимум 50% исходного покрытия. Для самих недельных
счётчиков этот дополнительный порог не применяется: наблюдаемый нулевой счётчик
правдиво описывает отсутствие ответов.

Нет импутации или переноса последнего значения. Сохраняются:
**null != 0; null != false; missing != skipped; not_applicable != missing;
no_obligations != исторический 0%.** Ноль Stage 4 при обязательствах — наблюдаемый
результат, хотя исходная привычка может не иметь отметки; эти два признака не смешиваются.

## Правила по типам

| Тип | Сводка |
| --- | --- |
| numeric | Mean, median, minimum, maximum, range, population standard deviation |
| ordinal | Те же описательные величины и распределение по значениям шкалы |
| boolean | `true_count`, `false_count`, `true_rate` среди наблюдаемых ответов |
| categorical | Частоты, доли среди наблюдаемых ответов, все связанные максимумом моды |

Основные числовые величины доступны с одного наблюдения; без наблюдений — null и
`insufficient_data`. Range одного наблюдения = 0. Standard deviation =
`sqrt(sum((x - mean)^2) / n)` описывает имеющуюся совокупность, доступно с двух
наблюдений; для константы равно 0. У SD отдельный `variability_status`.
Переполнение конечных чисел не выпускает NaN/Infinity: непредставимый результат
становится null с `numerical_overflow`; другие представимые числа сохраняются.

Шкалы mood/energy/wellbeing сохраняют распределение 1–5, включая категории с
нулевой частотой. Среднее и дробная медиана — описательные агрегаты, не более
точные исходные измерения; будущему UI следует выводить их с умеренной точностью
(например, один десятичный знак). Сервис не округляет промежуточные вычисления.

Порядок категорий берётся из реестра; дополнительные категории сортируются для
воспроизводимости. Это порядок отображения, **не числовая шкала**. При отсутствии
наблюдений доли null, `modes=[]`; при равенстве возвращаются все моды.
`true,true,false,null,null` даёт observed=3, missing=2, true_rate=2/3.

Тип и естественное зерно берутся из Stage 7A. Среднее недельных mean-признаков —
невзвешенное среднее наблюдаемых **недель**, не среднее всех дней. Для среднего по
дням следует выбирать исходную `state.*` переменную; source coverage показывает
число исходных ответов и не меняет вес недель задним числом.

## Привычки и Daily State

Динамические `habit.<id>.*` обрабатываются теми же функциями. Для status дополнительно
возвращается `habit_completion`: completed/done, missed, skipped, unmarked,
applicable (= eligible прошедшие даты и сегодня), `completion_rate_among_observed`
(done / все явные отметки). Это распределение отметок, **не новый score или
процент выполнения недельной квоты**. Для канонического выполнения доступны score,
веса, quota, completed_count и daily_completed_count из 7A/Stage 4.

Количество привычки хранит историческую `unit` в каждой точке из контекста 7A.
В сводке `units` перечисляет единицы наблюдаемых значений. Если единиц больше одной,
числовая сводка, rolling и trend подавляются с `incompatible_units`; сравнение также
подавляется при разных единицах между периодами. Ряд и покрытие сохраняются.
Конвертаций, количественных targets и новых формул scoring нет. Переименование
не меняет ключ. Binary-периоды quantity остаются `not_applicable`.

Sleep status остаётся категорией; sleep minutes — отдельным числом. Gaming flag и
gaming minutes, computer_overuse и computer_minutes независимы. Из минут никогда
не выводится субъективный overuse или другой флаг. Тексты не анализируются.

## Rolling и единая политика минимальных выборок

| Операция | Минимум |
| --- | --- |
| Raw counts/distributions, основные числовые величины | Нет порога для counts; 1 для чисел |
| Variability (population SD) | 2 наблюдения |
| Дневное rolling окно 7/28 дней | Полное временное окно; минимум 4/14 наблюдений |
| Недельное rolling окно 4/12 недель | Полное временное окно; минимум 2/6 наблюдений |
| Сравнение | В каждом периоде минимум 3 дня или 2 недели; coverage >= 50% |
| Trend | В каждой половине минимум 3 дня или 2 недели; coverage >= 50% |

Rolling trailing, включает дату/неделю точки, использует только `present` значения.
Окна начинают отсчёт **в выбранном текущем периоде**, без скрытого разогрева данными
предыдущего периода. До наличия полного временного окна — null/insufficient_data.
Пустые ячейки остаются календарными позициями, не уплотняются. Требуемое число
наблюдений — `ceil(window_size * 0.5)`, даже если часть позиций неприменима.
Каждая точка окна имеет date, window_start, window_size/unit, available_count
(число доступных календарных позиций, не наблюдений), observed_count,
required_count, coverage, status, mean. Для начала раньше date.min start=null.
Порядок: дата по возрастанию, затем размер окна по возрастанию.
Boolean/categorical возвращают `rolling=[]`.

## Незавершённые периоды

Выбран консервативный подход: **сводки и исходные ряды показывают доступные значения,
сравнение/направление/rolling незавершённой части подавляются**.

- Дневная точка `incomplete=true` для today и будущего; день становится завершённым
  на следующий календарный день. Даже заполненное сегодня не считается законченным.
- Недельная точка незавершена при `unfinished_week` (включая сегодняшнее воскресенье)
  или `partial_requested_week`. Полный недельный score не выдаётся за результат
  обрезанной части недели.
- Для отдельной недельной привычки также проверяются дни активности из канонического
  контекста: от 1 до 6 активных дней в полной неделе делает её неполной для аналитики.
  Для общего Stage 4 прогресса используется канонический `active_habit_days`.
  Нулевая активность остаётся отдельным отсутствием/неприменимостью.
- В week-контексте сохраняются границы недели/запрошенной части, elapsed counts,
  activity counts и `scope` (calendar_week / requested_elapsed_dates).
- Неполная точка делает сводку `incomplete=true`. Сравнение и trend всего такого
  периода подавлены; rolling подавлено только у окон, включающих неполную точку.
  Ранее завершённые окна продолжают работать.

Это также означает, что месячный/годовой запрос с обрезанными граничными неделями
имеет недельные сводки, но не получает недельную дельту. Для недельного сравнения
нужно выбрать завершённые целые Пн–Вс недели. Политика не подгоняет длины и не
пропорционально уменьшает канонические квоты.

## Сравнение периодов

Предыдущий период — непосредственно перед start, той же длины в **календарных днях**.
Например, 2026-09-01…2026-09-30 сравнивается с 2026-08-02…2026-08-31.
Для numeric/ordinal сравниваются means, для boolean — observed true rates.
Для categorical возвращаются обе распределённые сводки, все дельты null.

При достаточных завершённых сопоставимых данных:

```text
absolute_delta = current - previous
relative_delta = absolute_delta / abs(previous)
percentage_delta = 100 * relative_delta
```

Если previous=0, относительная/процентная дельты null, абсолютная остаётся доступной.
Модуль знаменателя даёт понятное направление изменения и для отрицательных generic
чисел. Для boolean absolute_delta — разность долей (0.1 = 10 процентных пунктов),
percentage_delta — относительное изменение доли.

Оба периода должны иметь одинаковое `eligible_count` и разницу покрытия <= 0.25
(25 процентных пунктов). Для weekly State means это применяется также к исходному
дневному покрытию. Иначе `coverage_mismatch`, числовые дельты null. Эта проверка
снижает риск сравнения несопоставимых охватов, но не является проверкой значимости
и не устраняет возможную систематичность отсутствующих наблюдений.

Приоритет причин: incomplete_period → incompatible_units → insufficient_data →
coverage_mismatch → вычисление (возможен numerical_overflow). Обе полные сводки и
покрытия всегда доступны, даже если дельта подавлена.

## Определение направления

Только numeric/ordinal. Метод `half_period_medians`:

1. Разделить календарные позиции ряда на две последовательные половины. Первая
   содержит floor(N/2) позиций, вторая остальные; пропущенные позиции не удаляются.
2. Проверить завершённость, единицы и минимальное число/покрытие каждой половины.
3. Вычислить медианы A/B наблюдений половин и population SD всех наблюдений.
4. Порог numeric: `max(0.05 * abs(A), 0.5 * SD)`;
   ordinal: `max(0.5 пункта шкалы, 0.5 * SD)`.
5. `B-A > threshold`: rising; `< -threshold`: falling; иначе stable (включая
   точное равенство порогу и константу с нулевой дисперсией).

Ответ раскрывает split_date (начало второй половины), оба числа наблюдений,
медианы, delta и threshold. При подавлении direction=insufficient_data и отдельный
status с причиной; boolean/categorical имеют not_supported. Направление —
детерминированное описание различия половин, не доказательство устойчивой тенденции,
не регрессия, не статистический тест и не обещание будущего изменения.

## Производительность, проверки и граница

Один dataset build включает оба периода (максимум 3660 дней — лимит 7A). Нет
самостоятельных запросов к habits/history/entries/State и пересчёта формул Stage 4.
Обычно 4 SELECT: привычки, версии, entries, State; наследуется пакетирование
selectin для >500 привычек. Срезы и индексы дневных строк по неделям создаются один
раз на период. Для каждой выбранной переменной — линейные проходы, сортировка для
медиан и ограниченные окна максимум 28 ячеек. Нет сканирования всего периода для
каждой точки окна, кеша, новых таблиц, flush/commit или миграций.

Тесты проверяют один build и четыре SELECT для 1 дня и високосного года с 12
динамическими привычками; полный логический dump БД не меняется, pending/dirty
объекты не flush-ятся, сериализация не делает SQL. Отдельные тесты покрывают
нулевые/отсутствующие значения, распределения, окна, сравнения, переполнения,
исторические единицы, частичные недели, границы дат и JSON/OpenAPI.

Stage 7B не добавляет frontend/dashboard/charts. Не реализованы correlations,
Pearson/Spearman, lag analysis, causality, factor rankings, recommendations,
prediction, automatic insights. Эти операции принадлежат следующим этапам.
Унаследованное ограничение 7A: прежние интервалы архивации после restore неизвестны.
