# Stage 7A — контракт набора данных

Stage 7A создаёт единственный канонический набор данных для следующих этапов
аналитики. Версия контракта: `7A.1`. Он вычисляется из существующих источников;
таблиц аналитики, миграций и сохранённых оценок нет.

Stage 7B реализован поверх этого контракта: [описательная аналитика и динамика](analytics-descriptive.md).
Чистая `builder.slice_dataset(dataset, start, end)` проецирует уже загруженный набор:
полный недельный прогресс сохраняется, State и requested coverage пересчитываются
из канонических дневных ячеек для выбранного поддиапазона. Источники не загружаются
повторно; контракт `7A.1` и семантика исходного endpoint не изменены.

## Вход и архитектура

Внутренний публичный API:

```python
from app.services.analytics import get_dataset

dataset = get_dataset(session, start, end, today=clock.today())
```

HTTP: `GET /api/analytics/dataset?start=2026-09-01&end=2026-09-30`.
Оба параметра обязательны, диапазон включительный, от 1 до 3660 дней.
Обратный или слишком длинный диапазон отклоняется до загрузки БД (HTTP 422).
Диапазоны длиннее лимита потребитель разбивает на части; при объединении нужно
дедуплицировать пересекающиеся календарные недели и пересчитать агрегаты наблюдений
из объединённых дневных строк, а не усреднять средние частей.

- `domain/analytics/types.py`: типы значений, переменных, дневных/недельных строк
  и отделённых от ORM входных снимков.
- `domain/analytics/variables.py`: детерминированный реестр переменных.
- `domain/analytics/builder.py`: чистая подготовка строк и агрегатов наблюдений.
- `services/analytics.py`: публичная точка входа и пакетная загрузка источников.
- `services/progress.histories_from_loaded`: общий со Stage 4 адаптер истории,
  включая архивную границу. Формулы `day_progress` и `week_progress` не скопированы.
- `schemas/analytics.py`: JSON/OpenAPI-схема того же контракта без второй модели данных.

Stage 7B+ получает переменные и строки отсюда, без самостоятельных запросов к
сырым таблицам. Чистый builder предназначен для уже подготовленных полных входов:
истории должны включать записи за все затронутые календарные недели.

## Форма ответа и переменные

Ответ: `contract_version`, `start`, `end`, `today`, `variables`, `daily`, `weekly`.
Строки идут по возрастанию даты. Каждый `values` содержит ровно все ключи своего
зерна из реестра, даже если привычка появилась или перестала действовать внутри
диапазона. В JSON ключи словаря `habits` — строковые представления целых ID.

Каждая переменная имеет `key`, русскую `label`, `type`, `grain`, `source`,
`missing_semantics`, при необходимости `categories`, `minimum`, `maximum`, `habit_id`.
Типы конечны: `numeric`, `ordinal`, `boolean`, `categorical`; зерно — `daily`/`weekly`.
Числа сохраняют целочисленный тип там, где это счётчик или шкала; средние и проценты
могут быть дробными. Категории представлены строками, логические ответы — boolean.

`daily.weekday` содержит строки `"0"`…`"6"` (понедельник…воскресенье),
`daily.month` — `"1"`…`"12"`, `daily.iso_week` и `weekly.iso_week` — `"1"`…`"53"`.
Это категории, не количественные измерения. `year`/`iso_year` — целые числа.
`daily.weekend` — суббота/воскресенье, без календаря праздников.
`daily.date_relation` — `historical`/`today`/`future` относительно переданного Clock.
Дата строки и начало недели — идентификаторы строк, остальные поля контекста
не входят в реестр аналитических переменных.

## Отсутствующие значения

Каждая ячейка имеет форму `{"value": false, "availability": "present"}`.
Непустое значение допускает только `present`. Для `null` обязательна причина:

| availability | Значение |
| --- | --- |
| `present` | Наблюдение, известный план, календарный признак или вычисленный результат |
| `source_missing` | Нет строки исходной записи |
| `field_missing` | Запись есть, конкретное поле не заполнено |
| `not_applicable` | Привычка не действует на дату или поле не относится к её конфигурации |
| `future` | Дата наблюдения/период ещё не наступили |
| `no_obligations` | Процент не определён: нет обязательств |
| `no_observations` | Для среднего нет ни одного наблюдения |

Таким образом, **null != false**, **null != 0**, отсутствие обязательств != 0%,
нет отметки != сознательный пропуск, неприменимость != отсутствие записи.
`present` не означает автоматически «пользователь наблюдал»: происхождение
показывает `source`. Например, обязательный вес — план, а процент — результат Stage 4.
Нет импутации нулями, false, предыдущими значениями или средними.
NaN/Infinity запрещены типом ячейки. JSON сохраняет null, false, 0, строки категорий
и целые значения шкал.

## Дневная строка и привычки

Дневная строка содержит `date`, `week_start`, `values`, `habits`, `state_source`.
Календарные даты не проходят через UTC datetime/JavaScript Date. Неделя — Пн–Вс;
`iso_year` может отличаться от календарного `year` на границе декабря и января.
Поддерживаются високосные годы и границы Python date; последняя неделя 9999 года
ограничена `9999-12-31`, поскольку даты следующего года не представимы.

`daily.score`, `daily.completed_weight`, `daily.required_weight` берутся из
`day_progress`. В процент входят только ежедневные обязательства. Прошедший день
с обязательствами без выполнений имеет 0%; день без обязательств — null с
`no_obligations`. Пропуски и отсутствие отметок не исключают вес из плана.

Ключ привычки: `habit.<habit_id>.<daily|weekly>.<feature>`. Переименование или смена
режима не создают новую переменную. Метка содержит стабильный ID; историческое имя
находится в контексте даты. Реестр включает объединение привычек, действующих хотя бы
в одной затронутой полной неделе, и привычек с сохранённой записью в этих неделях.
Поэтому привычка, создаваемая в пятницу, может присутствовать как `not_applicable`
в запросе за понедельник той же недели. Полностью посторонние привычки исключены.
Между разными запросами набор колонок может меняться; объединять нужно по ключу.

Дневные признаки привычки:

- `status`: только явные `done`, `missed`, `skipped`. Нет записи — `source_missing`.
- `quantity`: записанное количество, включая 0; пустое поле — `field_missing`,
  отсутствующая запись — `source_missing`, режим `binary` — `not_applicable`.
- `weight`: исторический вес действующей привычки.
- `required_weight`: вес дневного обязательства из Stage 4; у недельного
  расписания `not_applicable`, поскольку это не нулевое дневное обязательство.

`habits[id]` содержит `configuration` (`effective_from` и полный `HabitConfig`),
`applicable`, `entry` (сырой статус, точные `quantity_micro`, причина пропуска,
заметка). Статус и количество в контексте могут сохраняться даже вне обязательств:
это источник, не наблюдаемая аналитическая ячейка. Количество в `values` — JSON-число
через канонический `Quantity`; точные миллионные доступны в контексте без потерь.
Единица всегда берётся из конфигурации соответствующей даты. При смене единиц их
нельзя безусловно суммировать или сравнивать; Stage 7A не конвертирует единицы и не
строит среднее количества привычки. У текущей модели нет количественного target
или канонического отношения количества к target; эти признаки не изобретаются.

Используется версия, действовавшая **на конкретную дату**, включая исторические
режим, вес, единицу, расписание, предпочтительные дни и квоту. Same-day collapse
остаётся правилом Stage 2: замена версии на ту же дату меняет читаемый смысл этой
даты. Недельное расписание допускает отметки в любой активный день, в том числе
вне предпочтительных дней. Активность и архивная граница совпадают со Stage 4.
Архивный timestamp переводится из UTC в локальную дату существующим адаптером;
это единственная унаследованная зависимость исторической активности от timezone.

## Daily State

В реестре только намеренно выбранные поля Stage 5:

- `state.mood`, `state.energy`, `state.wellbeing` — ordinal, 1–5 или null.
- `state.alcohol`, `state.gaming`, `state.computer_overuse` — true/false/null.
- `state.gaming_minutes`, `state.computer_minutes`, `state.sleep_minutes` — numeric,
  целые 0–1440 либо null. Неизвестное время не превращается в ноль.
- `state.sleep_status` — categorical: `underslept`/`normal`/`overslept`/null.

Gaming и минуты сохраняются отдельно: true+минуты, true+null, false+null, false+0.
`computer_overuse=false` с `computer_minutes=180` сохраняется без изменений:
субъективная оценка и измерение независимы. `sleep_status` и `sleep_minutes` также
независимы. Никаких порогов, производных статусов или интерпретаций нет.
`note` и `alcohol_detail` остаются только в `state_source`, без признаков из текста.

## Недельная строка: два явных диапазона

Каждая затронутая неделя получает одну строку с устойчивым `week_start`, `week_end`
и ISO week/year в `values`. У строки есть **два явно обозначенных охвата**:

1. `progress_scope = calendar_week`: `weekly.score`, веса и признаки привычек
   используют **полную Пн–Вс неделю**, включая даты за пределами запроса.
   Загружаются и эти исходные записи. `week_progress` сохраняет полный недельный
   план и каноническую квоту без пропорционального уменьшения.
2. `state_scope = requested_elapsed_dates`: Daily State агрегируется **только по
   запрошенным датам <= today**. Внешние даты полной недели не попадают в эти средние.

Поля охвата: `requested_start`, `requested_end`, `requested_days`,
`elapsed_requested_days` (включает сегодня), `calendar_elapsed_days`,
`partial_requested_week`, `unfinished_week`, `active_habit_days` (даты полной
недели, на которых есть хотя бы одна действующая привычка любого расписания).
Они позволяют отличить обрезанный запрос, первую отслеживаемую неделю и текущую
незаконченную неделю. Сегодняшнее воскресенье ещё считается незавершённой неделей.
Ноль наблюдений в прошлом и полностью будущая часть недели различаются.

Пример: запрос Ср–Пт возвращает `requested_days=3`, `partial_requested_week=true`.
Недельное выполнение в понедельник входит в `weekly.score`, но настроение
понедельника не входит в среднее Ср–Пт. Нельзя трактовать этот процент как процент
только за три запрошенных дня. Для сравнений полных наблюдаемых недель потребитель
должен проверять охват и числа наблюдений.

Недельные признаки каждой привычки:

- `quota`, `completed_count` — только недельная компонента; для чисто ежедневной
  привычки оба `not_applicable`. Количество выполнений может превышать квоту.
- `daily_required_count`, `daily_completed_count` — дневная компонента; 0 допустим.
- `required_weight`, `completed_weight` — обе компоненты, с ограничением недельного
  зачёта квотой, как в Stage 4. Своей формулы оценки здесь нет.

При смешанной конфигурации недельная компонента берёт квоту, вес и предпочтительные
дни из **первой активной даты с недельным расписанием** этой недели. Поздняя правка
недельной конфигурации влияет на следующую неделю. Даты с daily-расписанием дают
только дневную компоненту. `habits` недельной строки сохраняет `weekly_effective_from`,
`weekly_weight`, `preferred_weekdays` и имя из канонического результата Stage 4.
Создание/архивация посреди недели не уменьшают уже начавшуюся квоту.

Для каждого поля State есть `weekly.state.<field>.observed_count`. Для numeric и
ordinal также `.mean` (тип numeric): сумма **только непустых** наблюдений / их число.
При нуле наблюдений mean — null/`no_observations`. Для boolean есть `.true_count`
и `.false_count`; их сумма равна observed_count. Нули этих счётчиков говорят об
отсутствии соответствующих ответов, а не о семи отрицательных ответах. Категории сна
не переводятся в баллы: для них есть только число наблюдений.

## Будущие даты

Будущие дневные строки сохраняются. Календарь, конфигурация и плановый вес известны;
score, completed_weight, State и применимые наблюдения привычек — null/`future`.
Неприменимость имеет приоритет для неприменимых полей привычки. Будущий запланированный
`skipped` сохраняется в исходном `habits[id].entry`, но не становится наблюдением.

Полностью будущая календарная неделя имеет null/`future` вместо процентов и выполнений;
плановая квота и обязательный вес сохраняются. Для полностью будущей **запрошенной
части** State даже счётчики имеют null/`future`. Если запрос начинается завтра, но
относится к текущей неделе, недельный прогресс всё ещё описывает полную текущую
неделю, а State — будущую запрошенную часть. Это определяется полями охвата.
Текущий день/неделя показывают live-прогресс Stage 4, включая ещё невыполненный план.

## Только чтение и эффективность

Обычно выполняются **4 SELECT**: identities, versions (с существующим joined area),
entries за охватывающие недели, State за запрошенный диапазон. SQLAlchemy selectin
может разбивать загрузку версий на пакеты при более чем 500 привычках; это зависит
от числа identities, не от числа дат. Нет запросов внутри дневных/недельных циклов.
Версии загружаются целиком, чтобы сохранить историю; записи ограничены диапазоном.
Вся подготовка строк и сериализация работают с отделёнными снимками без ORM.

Builder не создаёт/не меняет записи, не flush/commit, не материализует пропуски,
не нормализует историю. `session.no_autoflush` предотвращает запись даже при передаче
сессии с ожидающими изменениями; сам вызывающий код отвечает за последующий commit
своих изменений. Тест сравнивает полный логический дамп БД до/после, запрещает
не-SELECT SQL, проверяет неизменность pending/dirty состояния и одинаковые 4 запроса
для одного дня и високосного года с 12 привычками. Сериализация не делает запросов.

## Граница и ограничения

Stage 7A не содержит корреляций, значимости, доверительных интервалов, трендов,
лагов, рейтингов факторов, прогнозов, рекомендаций, текстовых инсайтов или UI
аналитики. Средние и счётчики — только детерминированная подготовка данных.

Унаследованное ограничение: модель хранит лишь текущую архивную границу; восстановление
очищает её, поэтому восстановить прежние архивные интервалы невозможно. Как и Stage 4,
legacy-архив без timestamp не создаёт обязательств, но его источники сохраняются.
Stage 7A не создаёт искусственную архивную историю или количественные цели.
