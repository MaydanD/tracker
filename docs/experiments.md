# Stage 10 — Experiments

Stage 10 позволяет описать **ограниченный по времени личный эксперимент** (гипотезу
и то, что пользователь меняет), а затем посмотреть, как **уже существующие** данные
Tracker соотносились с этим периодом: **до / во время / после**.

Это **описательный**, а не причинный анализ. UI никогда не пишет «эксперимент
улучшил» или «привело к»: он говорит «во время было выше/ниже» и «показатель
совпал с изменением периода». Эксперимент — не привычка: он не создаёт habit и не
участвует в daily tracking сам по себе.

## Архитектура

- `app.domain.experiments` — чистый доменный слой: lifecycle, сравнимые окна,
  покрытие, описательные сравнения и итоговая формулировка. Ни БД, ни часов, ни
  random: `today` и дата отмены передаются явно.
- `app.services.experiments` — orchestration и persistence. Загружает канонический
  Stage 7A dataset **один раз** на detail-запрос, поверх окна `before + during +
  after`, и берёт имена привычек одним метаданным запросом.
- `app.schemas.experiments` — типизированные контракты. Формат (длины, required)
  живёт здесь; продуктовые правила (порядок дат, длительность, политика правок,
  нормализация текста) — в домене.
- `app.api.routes.experiments` — тонкий слой: разрешает injected `Clock`, вызывает
  сервис, проецирует результат. Никакой математики в handler'ах.

Математика не дублируется: дневной прогресс, веса, streaks и Daily State приходят из
канонического dataset (который сам переиспользует Stage 4 progress и Stage 7 state).

## Data model

Таблица `experiments` (миграция `c3f1a7b24d90`, `down_revision = b2631e796164`):

| Поле | Смысл |
| --- | --- |
| `id` | Первичный ключ. |
| `title` | Короткое пользовательское название (≤ 120, непустое). |
| `hypothesis` | Что пользователь предполагает увидеть. |
| `protocol` | Что конкретно он меняет. |
| `start_date` / `end_date` | Запланированное окно, `start_date <= end_date`. |
| `cancelled_on` | Дата досрочной остановки, иначе `NULL`. |
| `created_at` / `updated_at` | Таймстемпы. |

**Статус не хранится колонкой.** Это одна детерминированная функция дат и
`cancelled_on`, поэтому lifecycle не может разойтись с календарём. Индекс — только
по `start_date`. Значения сравнений не хранятся: они пересчитываются.

## Lifecycle

```text
scheduled  — today < start_date
active     — start_date <= today <= end_date
completed  — today > end_date
cancelled  — cancelled_on заполнен (в любой момент)
```

`cancelled` перекрывает остальные, потому что отмена — явное действие пользователя.

## Окна: before / during / after

Длина `before` и `after` равна длине `during` (после отмены — фактически прошедшей
части). Окна соседние и не пересекаются:

```text
before   = [start - length, start - 1]
during   = [start, effective_end]
after    = [effective_end + 1, effective_end + length]
```

`effective_end = min(end_date, cancelled_on)` при отмене. Отмена до старта даёт
пустые окна — сравнивать нечего, и UI это честно показывает.

## Фаза

`ExperimentPhase` показывает, где стоит календарь: `scheduled` (сколько дней до
старта), `active` (день N из M), `completed`/`cancelled` (сколько дней «после»
уже собрано из полной длины). Использует injected `Clock`.

## Coverage и честность данных

Для каждого окна: `calendar_days`, `elapsed_days`, `observed_days`, `coverage`.
Наблюдаемым день считается только если пользователь реально что-то записал (отметка
привычки или поле Daily State). **Отсутствие данных ≠ ноль и ≠ провал**: неполный
день влияет на coverage, но не подставляется нулём.

Сравнение считается достаточным (`sufficient`), когда и `before`, и `during` имеют
≥ 3 наблюдаемых дня и покрытие ≥ 60 %. Иначе `summary` прямо говорит, что данных
недостаточно, а не показывает уверенную разницу.

## Что сравнивается

- **Общий прогресс** — средний дневной score (`daily.score`) по окнам, плюс
  `delta_before_during`, `delta_during_after`, `delta_before_after` в п.п.
- **Привычки** — доля выполненных обязательных дней (`done / obligation`) по окнам
  и `delta_during_vs_before`, с числом наблюдаемых дней.
- **Состояние дня** — средние по существующим полям Daily State (настроение,
  энергия, самочувствие, сон и т. д.); для boolean-показателей — доля.
- **Дневная серия** — сырые `score`/`energy` по дням; пропуски остаются пропусками.

Только `before vs during`, `during vs after`, `before vs after`. Никакого
causal inference, p-value engine, Bayesian/AB/ML. Формулировки нейтральные.

## Cancellation

Отмена сохраняет дату (`cancelled_on` из injected `Clock`), `effective_end`
становится датой отмены, `during` считается по фактически прошедшему периоду, и
`after` начинается сразу после. Запланированные, но не состоявшиеся дни в
`during` не попадают.

## Editing rules

- `scheduled` / `active` — можно менять даты и текст.
- `completed` / `cancelled` — даты **immutable** (история остаётся сопоставимой),
  текст можно исправить. Нарушение → `ExperimentStateError` (`experiment_state`).

## Overlapping experiments

Одновременные эксперименты **разрешаются**, но честно помечаются: detail показывает
`В этот период пересекался ещё N …`, чтобы одно вмешательство не выдавалось за
единственную причину изменений. Overlap считается по эффективным окнам, self
исключается.

## API

| Метод | Путь | Назначение |
| --- | --- | --- |
| `GET` | `/api/experiments` | Список (newest start first) + `owl`. |
| `POST` | `/api/experiments` | Создать. |
| `GET` | `/api/experiments/{id}` | Detail: `experiment`, `overlaps`, `analysis`. |
| `PATCH` | `/api/experiments/{id}` | Частичная правка. |
| `POST` | `/api/experiments/{id}/cancel` | Досрочно остановить. |

`analysis` содержит `windows`, `overall`, `habits`, `state`, `series`, `sufficient`
и `summary`. Отдельного `/complete` нет: завершение следует из даты.

## Owl integration

Сова (Stage 9) получает минимальный experiment-контекст и **переиспользует
`owl_insight`**, новых PNG нет:

| owl_id | Приоритет | Когда |
| --- | --- | --- |
| `experiment_active` | 10 | Есть активный эксперимент. |
| `experiment_no_data` | 20 | Завершён, но данных мало (`sufficient == false`). |
| `experiment_completed` | 30 | Завершён, есть что сравнивать. |

Состояние встроено в `ExperimentListRead.owl` (страница «Эксперименты»), одним
баннером, без переписывания Stage 9.

## Frontend

`/#/experiments` — список (status, даты, фаза, гипотеза), форма создания/правки и
`/#/experiments/:id` — detail с timeline `До | Эксперимент | После`, сравнением
общего прогресса, состояния дня и привычек, графиком по дням, качества данных и
нейтральным итогом. Весь текст русский; сырые enum-значения в UI не попадают.
График рисует пропуск как пропуск (никогда как нулевой столбик).

## Ограничения

- Описательная статистика без доказательства причинности.
- Нет RTC/AB/p-value, автоподбора гипотез, шаблонов, уведомлений, шеринга.
- Overlap предупреждает, но не блокирует.
- `after` может быть неполным — это показывается явно.
