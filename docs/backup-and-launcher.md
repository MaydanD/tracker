# Резервные копии и Windows launcher

## Исходное состояние

Работа начата с чистой ветки `main`, HEAD `c005b2bfb7d3cd38425560ae96ce5596ede517a1`.

- Официальный ZIP `/api/backup`: `manifest.json` + `data.json`, формат v1, явный список семи доменных таблиц. JSON/CSV — отдельные экспорты.
- Restore: проверка ZIP, подписанное подтверждение конкретного файла, атомарная замена доменных данных и страховочная копия. File picker сохранён.
- Settings уже содержал подключение, скачивание, экспорты и восстановление.
- `app_metadata` — существующая таблица key/value. Runtime-настройки читаются из окружения и `.env`; хранилища секретов не было.
- До изменений Dashboard напоминал только первого числа и опирался на localStorage/sessionStorage.
- Штатный backend script выполнял Alembic и запускал приложение с reload; frontend script запускал Vite и устанавливал зависимости при их отсутствии.

## Состояние и календарь

Одна запись `app_metadata.key = backup_settings_v1` содержит JSON: UTC-дату последней успешной копии, локальный календарный месяц, тип `download`, `telegram` или `auto-telegram`, последнюю дату Telegram, chat ID, флаг автоотправки, результат подключения, безопасный текст ошибки и служебную блокировку/срок повтора. Новых таблиц, столбцов и миграций нет.

Месяц берётся из существующего `Clock.today()`, UTC-время — из `Clock.now()`. Это сохраняет правильную семантику вблизи полуночи и на границе месяца. Reminder показывается, если успешной копии текущего месяца нет, включая первое открытие 8-го числа. Старые localStorage-флаги не используются.

Скачивание считается успешным после создания официального ZIP на backend. Нельзя подтвердить средствами HTTP, что пользователь затем действительно сохранил файл в браузерном диалоге. Экспорты JSON/CSV и внутренние страховочные копии не заменяют ежемесячную пользовательскую копию.

Для Telegram дата меняется только после успешного ответа `sendDocument`. Временный архив, создание которого завершилось, но отправка не удалась, успешной копией не считается. Restore сохраняет локальные настройки интеграции, поскольку заменяет только доменные таблицы.

Frontend обновляет состояние после скачивания/отправки, при возврате в окно и переходе между страницами. Пока отправка выполняется, статус опрашивается раз в две секунды. Dashboard содержит только небольшое напоминание и переход в Settings.

## Telegram и секрет

Стандартный `http.client.HTTPSConnection` выполняет HTTPS-запросы к фиксированному `api.telegram.org`; новых библиотек нет. Проверка — `getMe` и `getChat`, без загрузки ZIP и без тестового сообщения. Поддерживается личный чат. Для отправки используется multipart `sendDocument`, тот же официальный ZIP, имя `tracker-backup-YYYY-MM-DD.zip`, русский caption.

Сетевой timeout — 45 секунд на операцию сокета. ZIP свыше 50 МБ отклоняется с предложением скачать локально. HTTP/API-ошибки и timeout переводятся в безопасные русские сообщения; исходные URL, ответы Telegram и exception-тексты не выводятся. Ответы `429` не запускают автоматические немедленные retries. Документация API: https://core.telegram.org/bots/api#senddocument.

Токен хранится в `<resolved_data_dir>/telegram-token.secret`, записывается через временный файл и atomic replace. Он не помещается в SQLite, поэтому отсутствует как в официальных ZIP/экспортах, так и в физических SQLite-копиях при запуске. Файлы `telegram-token.secret*` исключены из Git. Значение не возвращается frontend; ответ содержит только `token_saved`. После сохранения поле пароля очищается. Некорректный ввод также не отражается в API-ошибке.

Trade-off: это локальный незашифрованный файл. На POSIX создаётся с правами 0600, на Windows действует унаследованный ACL каталога данных. Это не защита от процессов, уже имеющих доступ к данным пользователя. Vault/KMS и дополнительные зависимости не вводятся; токен при переносе официального ZIP нужно указать заново. Не публикуйте каталог данных целиком.

Новые действия отклоняют cross-site запросы и неизвестный Origin: одного CORS недостаточно, чтобы запретить стороннему сайту простой POST на localhost. Приложение остаётся локальным single-user сервисом без отдельной авторизации.

## Автоотправка и повторные запросы

Проверка выполняется в фоновой задаче при старте backend и через `/api/backup/auto` при загрузке любого раздела приложения, смене даты или возврате в окно. Условия: включён флаг, есть конфигурация и нет успешной копии текущего месяца. Успешное локальное скачивание также подавляет автоотправку до следующего месяца.

`BEGIN IMMEDIATE` атомарно проверяет и записывает claim в SQLite. Сеть работает за пределами SQL-транзакции. Claim действует 10 минут, имеет уникального владельца и виден другим вкладкам/экземплярам backend. Конкурентная ручная операция получает 409, автоматическая пропускается. Сохранение настроек на время операции заблокировано. После ручной или автоматической отправки действует 30-секундный предохранитель от повторного нажатия.

Перед сетевой операцией сохраняется срок следующей автоматической попытки: через сутки. Ошибка не отмечает месяц успешным; сообщение остаётся в Settings, reminder сохраняется. Перезапуск и refresh не сбрасывают паузу. Срок — разрешение повторить при следующем открытии, а не фоновый таймер. После аварийного завершения claim истекает самостоятельно, автоматическая пауза остаётся.

Telegram Bot API не предоставляет ключ идемпотентности для sendDocument. Если Telegram принял документ, а ответ потерялся или приложение аварийно завершилось до записи успеха, невозможно гарантировать строго одну доставку. В таком случае дата не обновляется; перед ручным повтором следует проверить чат. Автоматический повтор отложен на сутки.

## API

| Метод | Путь | Назначение |
|---|---|---|
| GET | `/api/backup/settings` | Безопасное состояние и `reminder_due`, `in_progress` |
| PUT | `/api/backup/settings` | Сохранить `{token?, chat_id, auto_enabled}`; отсутствие token сохраняет прежний |
| POST | `/api/backup/telegram/check` | Проверить бота и доступность личного чата |
| POST | `/api/backup/telegram/send` | Создать официальный ZIP и отправить |
| POST | `/api/backup/auto` | Выполнить защищённую ежемесячную проверку |
| GET | `/api/backup` | Существующий download; теперь записывает дату после генерации |

Остальные export/validate/restore endpoints и формат ZIP не изменены.

## Launcher

`start-tracker.bat` использует `%~dp0` и вызывает один `scripts/start-tracker.ps1`. Именованный mutex, привязанный к корню проекта, сериализует параллельные запуски. Backend проверяется через health с идентичностью Tracker и ready; frontend — по странице Tracker и проксированному health. Занятый чужим или неготовым сервисом порт приводит к понятной ошибке.

Запуск выполняется существующими `dev-backend.ps1` и `dev-frontend.ps1` в скрытых PowerShell-процессах. Добавлен `-NoReload` для стабильного runtime-запуска; обычный ручной dev-запуск по-прежнему поддерживает reload. Ошибка Alembic прерывает запуск. Vite привязан к 127.0.0.1; отсутствие зависимостей требует одноразового setup вместо неявной установки.

Ожидание сервиса ограничено 90 секундами; при завершении владельца ожидание прекращается раньше. PID и время создания записаны в `.data/launcher/processes.json`, stdout/stderr — рядом. Повторный BAT не порождает новые сервисы, только открывает браузер. При ошибке BAT вызывает pause.

`stop-tracker.bat` останавливает только сохранённых владельцев с совпадающим временем создания и их дерево потомков; перед остановкой сверяет время создания каждого процесса. Нет остановки по общему имени python/node. Сервисы, запущенные вне launcher, он не завершает.

- Backend: календарные границы, запись успеха/ошибки, отсутствие токена в API/ZIP/SQLite-копии/логах, fake HTTPS transport, точные байты официального ZIP в multipart и существующий validate/restore, concurrency, пауза retry, повторный backend, ограничения Origin.
- Frontend: Settings/Telegram states, очистка токена, sending/loading/disabled/errors, месячное напоминание, исчезновение после успеха без reload; существующие picker/restore regression tests.
- `powershell -NoProfile -File scripts/test-launcher.ps1`: синтаксис PS, wrapper/error handling, mutex/readiness, PID reuse, повторный запуск и занятый порт без реального запуска процессов.
